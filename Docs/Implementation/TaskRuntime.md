## Runtime choice and reviewer familiarity

**Trial oneTBB first; choose by demonstrated fit and code removal.** Its documented use around rendering and content tools gives the strongest evidence here for familiarity to NVIDIA and AMD reviewers. This is an inference from visible projects, not a survey of reviewers or proof that it is the most-used game-engine scheduler. Reviewer familiarity is a tie-breaker after behavior, supported APIs, maintenance cost and measured overhead pass. Public repository stars, CUDA support and a vendor's use of a dependency do not establish suitability for Sparkle.

## Ownership and removal

One selected runtime and one authority per responsibility are mandatory. This table defines the boundary; the caller map applies it to concrete files.

| Responsibility | Single authority / retained engine policy | Replaced machinery to delete |
| --- | --- | --- |
| Runnable scheduling and partitioning | Upstream owns queues, workers, stealing, wakeup and range scheduling. Host composition sets the total capacity budget. Multiple native arenas/executors need proven isolation under that budget. | `Private/Scheduling/`, custom `ParallelFor`, per-module runtime facades and uncoordinated per-module pools. |
| Dependency readiness | Upstream edges/joins release work; domain owners declare meaningful stage order and required inputs. | `Private/Graph/`, `Public/TaskGraph.h`, local graph compilation/storage, handle validation and prerequisite counters. |
| Cancellation intent and lifetime | Each existing operation owner holds its authoritative stop source and children; standard tokens carry intent. | Results and permission to destroy | The domain owner publishes one typed outcome after required cleanup and borrowed access settle. | Prepared notifications | The sink owns payload admission/coalescing/close and its bounded payload queue. Upstream alone schedules invocations. | Generic dispatch subsystem, local runnable queues and duplicate ready-state registries beyond the required sink gate. |
| All-zero reference execution | The same workload owner directly calls the same kernels and domain checks in deterministic order. | `SerialTaskExecution` and any second scheduler, graph interpreter or backend abstraction for the synchronous route. |
| Diagnostics and build integration | Upstream observability plus existing domain diagnostics; direct upstream target usage with truthful public/private visibility. Keep it in the existing domain owner; remove forwarding-only classes, empty runtime modules and speculative interfaces. Stage 1 found no owned production `TaskEvent` caller or direct external `AddNested` caller. `ParallelFor` uses `AddNested` internally: preserve its range/join behavior through upstream primitives, without reproducing the generic nesting API.

For each mutable fact, identify one source and who may change it in the existing report. Copies/views needed by another lifetime must have a producer, publication boundary and invalidation rule; they cannot become another writable authority. Payload queues, resource budgets and generation checks remain domain responsibilities, distinct from runnable scheduling. Reject duplicate dependency-readiness bookkeeping, local runnable-selection engines and competing cancellation/result controllers around upstream.

Stage 1 fixes the reduction budget for total owned infrastructure, public surface and state/failure paths. Count caller-side futures, gates, caches and synchronous orchestration as well as the deleted module; exclude unchanged kernels and fetched source, reporting upstream build/package cost separately. Renamed/relocated mechanisms still count. Full module deletion and the ownership boundary are mandatory regardless of line count. Fill budgets before trial results and keep them fixed.

## Simplify the connected callers

Convert the complete affected call paths: work construction, execution dependencies, result consumption, lifetime closure, public signatures and build/package membership. Remove old API workarounds as their responsibility moves upstream. Each retained abstraction/state field needs a current consumer and domain invariant. Keep unrelated redesign and speculative features outside this migration.

The delivered architecture must let a reviewer follow world extraction, scene preparation, recording and submission in their domain owners without learning a second Sparkle task model. Rendering decisions and CPU/GPU lifetime stay explicit; generic scheduling must cease to be an engine subsystem. A smaller Tasks directory, renamed task types or library calls behind the old design cannot satisfy this outcome.

Use the least machinery supplied by the selected runtime: native ranges for independent batches, native edges/joins for meaningful staged dependencies, direct submission for one operation and standard stop tokens with existing owner lifetimes. Indexed domain results replace generic per-node lookup. Do not turn every body into a graph, construct a pool per operation, retain cached padding graphs or add a universal parallel/serial runner. The zero-worker branch calls the same typed kernels directly in deterministic domain order; it has no generic graph interpreter or duplicated algorithms.

### Architecture and removal gate

Before stage 2, write the intended final owner paths into the existing report and apply them to the hardest real consumers. At every conversion checkpoint, reconcile that map against the actual diff. Keep one owner for scheduling/dependency readiness, one domain stop intent, one authoritative result and one admission account per invariant. A native completion observer must not become a second mutable status registry. Distinguish the small required crash coalescing gate from a general runnable queue.

Apply Engineering's existing-equivalent search before introducing or relocating any function, type, record or mechanism. Search by behavior and callers across owned sources, public headers, scripts, CMake and package inputs. Extend the matching owner when the invariant and lifetime coincide; explain distinct contracts before retaining similar pieces. Every added piece must reconcile with the counterpart ledger, including additions absent from the original consumer map. Delete superseded producers, forwarding callers, state, files and build entries in the same conversion checkpoint; compatibility paths and feature switches cannot leave two authorities behind.

Review separation of concerns and single responsibility at function, type and owner boundaries using the [engineering rules](../Engineering.md#module-boundaries). Keep code sharing an invariant or lifetime together. Orchestration should expose the domain steps in order; substantial algorithms and state transitions stay with their owner. Extract helpers around cohesive operations or independently changing responsibilities, then review the caller and helper together. Use [paragraph spacing](../CodeStyle.md#formatting-and-paragraphs) to separate logical phases and keep cohesive statements grouped.

The fixed footprint budget is a delivery gate, not a target to fill. Delete all 43 Tasks files/3,820 physical lines and every retired public API. Across the entire connected change, require at least 1,528 lines of net first-party infrastructure reduction, at most 2,292 new or relocated integration lines, at most 10 new public domain execution-boundary declarations, 12 new or relocated mutable infrastructure fields and 12 infrastructure rejection/cleanup sites. Count CMake, inline/template code and mechanisms moved outside Tasks; exclude unchanged kernels and upstream. Enumerate the retained surface and state individually. Passing a line budget cannot excuse an owned scheduler, facade, mirrored controller or unnecessary abstraction.

Use the same file/function scope and repository formatting on both sides of the count. Include nested records and inline state rather than hiding them behind one outer field. Do not compress code, remove necessary domain checks or reproduce unused generic event/handle/scope capabilities to satisfy old API-shaped fixtures. Preserve existing tests and adapt their actual workload claims; retiring a test still needs the agreement required by Engineering.md.

Review the final code in three directions: from one rendered frame to submission/retirement, from one cancelled operation to final capture release, and from each former task mechanism to its sole upstream primitive or necessary domain owner. Require both fewer maintained mechanisms and simpler connected callers. If supported upstream primitives cannot meet the preservation rules within this integration boundary, reject that candidate; do not build a framework to rescue it or relax the workload contract.

The [JSON migration](JSON.md) may touch the same diagnostic/process owners. Keep serialization with its established owner and stop/admission/settlement with the operation owner; neither migration may add duplicate payload models, publication state or exception controllers. Reconcile the combined files and refresh only affected baseline receipts when another migration lands. Do not mix source/products from separate candidates or expand this replacement into an unrelated renderer redesign.

## Behavior the design must preserve

### Ordering, failure and cleanup

[oneTBB graph cancellation](https://github.com/uxlfoundation/oneTBB/blob/v2023.2.0/doc/main/tbb_userguide/cancel_a_graph.rst) prevents unstarted nodes from running. [An exception escaping a node](https://github.com/uxlfoundation/oneTBB/blob/v2023.2.0/doc/main/tbb_userguide/catching_exceptions.rst) can cancel the graph too. Neither operation ensures a successor used for cleanup executes. Taskflow's cancellation has the same relevant successor hazard.

For graphs with required cleanup, use cooperative domain cancellation: normal bodies inspect a stop token, suppress their side effects when stopped or when required inputs failed, and still deliver their typed terminal outcome through upstream edges. Catch expected domain failures/exceptions at the work boundary. Independent branches retain the current opportunity to finish; failure blocks affected consumers. Aggregate failure takes precedence over cancellation and retains useful failure attribution.

Keep the required finalizer outside native cancellation suppression. In the proposed oneTBB design, the completion/cleanup path stays schedulable while domain work observes stop; do not call native graph/context cancellation on that path. Also handle rejection before admission and an unexpected runtime exception around the owning invocation. The owner publishes completion exactly once after running work, finalizers and borrowed captures settle. RAII releases acquired resources, but a destructor inside a body that never started cannot perform its operation-completion callback.

The concrete proof is [LauncherOperationService](../../Tools/Launcher/SparkleLauncher/Private/Gui/Operations/LauncherOperationService.cpp): its cleanup continuation clears `m_bOperationRunning` and invokes completion even if cancellation prevents the operation body from starting. Preserve that behavior, callback routing and retry admission. Never report cancelled/failed work as successfully published output.

Shutdown closes admission first. Drain finishes admitted normal work; cancel suppresses queued normal side effects and lets running bodies and required cleanup settle. Both close prepared dispatches and release captures before runtime destruction. Repeated shutdown must remain safe, and a worker must not join its own execution capacity.

### Parent/child ownership and timed settlement

Application, document/world, asset-generation and tool owners retain their actual children and cancellation lifetime. Forward a parent stop request to those children, close admission and join them before releasing parent data. Cancelling one child must leave its parent and siblings usable. A new request after closure is rejected before side effects. Keep stale-generation rejection and resource accounting with their domain owners.

Use standard stop sources/tokens/callbacks and the existing owner relationships rather than rebuilding `TaskScope` as another generic tree. [oneTBB contexts](https://github.com/uxlfoundation/oneTBB/blob/v2023.2.0/doc/main/reference/source/task_scheduler/scheduling_controls/task_group_context_cls.rst) describe execution-context relationships; they do not automatically reproduce Sparkle's application/document ownership. Use explicit contexts and verify the selected source; do not rely on ambient nesting or construction-thread coincidence.

Keep stop callbacks alive for the full child lifetime, handle a parent already stopped at child admission, and exercise callback reentrancy/destruction races. Do not request stop or invoke user completion under a lock those callbacks can acquire. Reentrant Launcher completion may admit the next operation; settlement of the old operation must not clear or access the new operation's state.

The current consumers use zero-time polling, bounded joins and owner-thread teardown. `graph::wait_for_all()` is an unbounded wait, so it cannot implement a timed join by substitution. Use a domain completion signal/future and an absolute deadline for host observation. A timeout returns with the operation and all borrowed storage still alive; it grants no destruction permission. Close and settle children within the same deadline budget. Keep owned work alive through a later successful join and release captures before reporting settled. Workers express dependencies through upstream primitives instead of blocking on their own executor's completion.

Distinguish result readiness, callback/body exit and permission to destroy storage. Publishing a promise inside a terminal node does not prove the node has returned or the graph is quiescent. The [selected oneTBB graph destructor](https://github.com/uxlfoundation/oneTBB/blob/v2023.2.0/include/oneapi/tbb/flow_graph.h) itself calls `wait_for_all()`. A timed observation must not be followed by a hidden blocking destructor or destruction of live nodes/captures. Specify the last access to borrowed data, the object retaining unfinished work and the final release point. Exercise timeout followed by continued operation, successful later join and teardown. Do not add a helper thread or `std::async` waiter to conceal an unbounded wait.

Check native lifetime primitives separately: [task_arena destruction is not a join](https://github.com/uxlfoundation/oneTBB/blob/v2023.2.0/doc/main/reference/source/task_scheduler/task_arena/task_arena_cls.rst), while [task_group requires wait before destruction](https://github.com/uxlfoundation/oneTBB/blob/v2023.2.0/doc/main/reference/source/task_scheduler/task_group/task_group_cls.rst). A deferred handle already participates in its group's wait even before scheduling. Any prepared-handle design must release unused handles on idle close, settle scheduled handles and keep their group/context alive; otherwise close can strand its own wait. Native wait APIs whose names mention a task are not evidence of a wall-clock timeout. Do not weaken destructor exception contracts or suppress a missing wait to silence integration warnings.

### Reentrancy, thread ownership and range storage

The selected [work-isolation contract](https://github.com/uxlfoundation/oneTBB/blob/v2023.2.0/doc/main/tbb_userguide/work_isolation.rst) permits a waiting thread to execute unrelated available tasks, including another outer-loop iteration. Before conversion, identify locks, thread-local state, COM apartments, borrowed scratch and recording leases held across every native wait/nested algorithm. Prefer releasing an unnecessary lock or removing the nesting; where isolation is necessary, prove the supported native boundary and its progress. Isolation is not a dedicated worker reservation. Add a controlled reentrancy case that would reacquire a held non-recursive lock or overwrite borrowed TLS, without turning the fix into a Sparkle dispatch layer or changing the lock merely to hide the conflict.

`task_arena::execute` may run on the entering application thread. Distinguish required affinity from incidental old-pool placement for each owner before judging compatibility; any changed placement remains an explicit preservation decision until owner checks establish it. Keep GUI/coordinator-only work on its owner and exclusive lease operations on their valid executing thread. A native arena slot is not an OS thread identity, a persistent scratch index or a substitute for actual-thread COM initialization. Include relevant floating-point state in CPU-output comparisons where workers inherit different settings.

Use the [selected partitioner guarantees](https://github.com/uxlfoundation/oneTBB/blob/v2023.2.0/doc/main/tbb_userguide/Partitioner_Summary.rst): default auto partitioning does not make grain size an upper bound on body range length. Preserve storage/admission bounds using an appropriate native algorithm/partitioner and existing domain storage, not a copied range scheduler. Index results and leases by stable domain item/chunk identity; never assume one body per worker or deterministic completion order. Exercise odd counts, ranges larger than former capacities, nested work and repeated reuse while checking bounds, non-overlap and ordered merge/publication.

### Deterministic caller-thread execution

When every worker count is zero, select the synchronous domain path before scheduling or initializing asynchronous work. Call the same kernels in fixed dependency order and use ordinary deterministic range loops. Submission/launch returns settled, every body/finalizer runs on the invoking thread, and no task worker or deferred callback is introduced. The invoking thread can be the render coordinator; `r.ThreadedRenderer` controls that separate ownership thread. Exercise both host arrangements without claiming all-zero task counts eliminate every engine thread. Remove `SerialTaskExecution.cpp`; fixed workload orchestration must not grow into another generic DAG interpreter.

An arena limited to one participant is insufficient evidence of this contract.
