## Protected concurrency and data-oriented architecture

**Removing multithreading is prohibited as a cleanup strategy.** Earlier removal answers retire optional capabilities or unnecessarily complex mechanisms, never the parallel execution capacity of retained work. This clarification governs every decision below, including GameFramework, Editor, Renderer, RHI, Launcher, cooking and compilation. Preserve the recorded feature cuts; revise their implementation boundaries wherever they implied serial replacement.

| Owner / execution boundary | Required retained design |
| --- | --- |
| GameFramework / game thread | Game-thread ownership of mutable world state; data-oriented component/resource storage; independent transform, animation and extraction ranges run as bounded worker jobs with explicit dependencies and deterministic merge/publication. |
| Editor / UI owner | Respect host UI affinity; inspect safe snapshots/borrowed views and apply world edits on the owning game-thread boundary. Expensive import, save preparation and inspection work stays off interactive frame lanes where independent. Editor is a module boundary, not a requirement for an invented extra dedicated OS thread. |
| Renderer / separate render thread | Keep a distinct render-thread owner and bounded game-to-render handoff. Preserve parallel scene preparation, frame-graph work and eligible command recording with immutable inputs and scoped outputs. |
| RHI / recording workers and submission owners | Preserve per-worker/per-context command allocator/list ownership, concurrent recording where legal, queue-specific submission ownership and thread-safe resource/descriptor lifetime. Keep D3D12/Vulkan queues, cross-queue dependencies, fences and deferred retirement. Do not replace this with one global recording lock or serialize independent passes. |
| Loading / cooking / build tools | Keep bounded parallel I/O/decode/preparation/compile work with backpressure and one clear operation owner. One owner does not mean one worker. Coordinate only genuine artifact/data conflicts; independent work remains concurrent. |

Keep contiguous iteration, stable resource handles, per-range outputs, cache-aware partitioning and reuse. Avoid per-instance resource duplication, unnecessary full snapshots, false sharing and coarse global locks. Removing a feature may remove its exclusive jobs; retained workloads must keep their dependency-correct parallel decomposition. Optimize useful throughput and overlap under CPU/memory/I/O limits, not raw thread count; preserve necessary ordering and native UI/API affinity.

For every row, implementation acceptance must identify the retained producer, worker/owner, consumer, data layout, handoff and retirement boundary. Compare retained-scene output, frame overlap/latency, load time and peak memory under representative threaded runs. Independent work must remain schedulable in parallel; accidental global barriers or new game/render stalls block completion. A serial/reference run can be measurement evidence, never a proposed cleanup replacement. This is a design requirement, not a claim that the current implementation has already passed that audit.

### How to read removal footprints

Every remaining decision includes its removal footprint. The file-selection receipt records `8104b90c8`; source owners remain subject to final-consumer checks. Completed cuts are excluded from this worksheet and its prospective savings. Figures for outstanding work are measured baselines, not implemented before/after diffs.

| Label in the capability cell | Meaning for your decision |
| --- | --- |
| **If removed, gross baseline** | Capability-specific whole files and their physical text lines, plus separately measured removable function/record spans in shared files. This is the counted existing code to retire; caller/build cleanup may add savings, while any required replacement subtracts from net savings. Final last-consumer checks still apply. |
| **Net savings unproven; shared/replacement scope** | A bounded measured owner area, not a deletion quote. Some behavior must survive or move. Do not treat all of its files/lines as savings; a smaller replacement is needed before a net figure is defensible. |
| **Alternative removal baselines** | A choice first needs an explicit narrower option, such as keeping raster versus ray-traced GBuffer. The alternatives are not additive. |
| **0 current/further code savings** | A policy/future-work decision, already retired implementation, data-only restriction or an expression edit that does not establish a physical line reduction. Do not invent a code saving to justify it. |

Counts include headers, implementation, shaders, scripts and relevant text configuration/data; scene rows explicitly include level/catalog text, and maintained patches count diff-file lines. Blanks/comments count, matching the module baseline convention. Binary assets, thumbnails, fetched upstream source, generated outputs, build-cache bytes and SDK binary payloads are excluded. A scene removal can save substantial asset space even when its code/text figure is small; that requires a separate dependency-aware byte inventory.

**Do not add row totals.** AP-03 is inside RE-04; ED-08/ED-21 share undo code; IM-03/RV-05 share PLY; several original and detailed questions name the same mechanism. Partial spans can also overlap a whole-file retirement. The ignored file-level receipt `build/validation/portfolio-footprint-20261125/decision-footprints.json` records each selection, partial line range, source hash, overlap and caveat. Figures are first-party maintenance baselines, not measured build/runtime gains. Protected parallel jobs, data-oriented storage, per-thread recording contexts and synchronization are not deletion savings; revised mechanism boundaries require a real net diff before claiming a reduction.
